The Most Expensive Word in AI Is “Done”

Remco Vroom · 19 July 2026 edition · 5 min read

Published 4 September 2026 · Catch-up edition for 19 July 2026.

AI-generated conceptual illustration, created with Higgsfield.

A confident completion message is useful only when the promised result exists.

The report is finished. The campaign is ready. The customer record has been updated.

Three reassuring sentences. Three different things to verify.

An agent's final message is often the easiest thing in the workflow to read. That makes it tempting to use the message as proof that the work succeeded. For a business leader, this is a small habit with potentially expensive consequences.

You need a definition of done that lives outside the agent's own description of its performance.

Begin at the receiving end

Consider an illustrative customer-research assignment. The agent returns a polished document with an executive summary, recommendations, and a list of sources. It looks complete.

But the team needed a decision on which customer segment to prioritize. The document discusses several segments without comparing them on the agreed criteria. A key citation does not support the adjacent claim. The recommendation depends on an assumption that has been presented as a fact.

The output exists. The assignment remains unfinished.

Now consider a different workflow that updates a customer record. Here, completion requires the right change in the right record. A beautifully written summary of the intended update cannot establish that the update actually happened.

Start your definition of done with the person or system receiving the work. What must be true for that recipient to proceed without reconstructing the task?

Separate existence, usefulness, and authorization

I would ask three questions at the end of an agent workflow.

Does the result exist where it should? A document should open. A record should contain the intended values. A saved file should be available to the person who needs it. If an action failed, the completion message should say so.

Does the result meet the agreed standard? A proposal needs accurate commitments, relevant evidence, and a usable recommendation. An analysis needs the right comparison and visible uncertainty. Quality belongs in the definition of the assignment.

Was the work completed within its authority? An output can be accurate and still have been sent to the wrong audience or produced using information the workflow should not access. Acceptance includes the boundaries under which the work was performed.

These questions are complementary. Passing one does not compensate for failing another.

Those are useful disciplines for business workflows as well as engineering tests. Demystifying evals for AI agents.

Make the standard observable

“High quality” is a preference until people can explain what it means.

For the research assignment, the standard might require a comparison against the agreed criteria, sources that support the material claims, and a clear separation of findings, assumptions, and recommendations. The reviewer should be able to locate each element quickly.

For a record update, the standard might be a confirmation from the destination system and a check of the fields that were supposed to change. Ask your technical owner how the workflow verifies the outcome and handles partial success.

Be precise about the important parts and flexible about the rest. A useful answer may have a different structure from the example you originally imagined. You want the test to recognize legitimate success, not reward imitation of one preferred sentence.

Some checks are straightforward: a required field exists, a link opens, a total reconciles. Others need judgment: the recommendation addresses the customer's actual problem, or the tone fits a difficult conversation. Give each check to a method suited to the job.

Keep the awkward examples

When a reviewer catches an error, preserve a suitably anonymized example of the input, the failure, and the expected behavior. Add it to the small set of cases you use before changing the workflow.

Include routine work, incomplete inputs, conflicting information, and cases where the correct response is to ask for help. Revisit the set as real work exposes new problems.

Keep some evaluation examples separate from the examples used to tune the prompt. Otherwise the workflow can look better because it has learned your rehearsal material. That is weaker evidence than succeeding on a fresh, representative task.

A single successful run is encouraging. Several consistent runs across relevant cases are more useful. Neither proves that every future task will succeed. Continue checking real outcomes in proportion to their consequences.

Your one action this week

Take the last agent output your team accepted. Write down three things that had to be true for it to count as done. Then find the evidence for each.

If the only evidence is the agent saying it succeeded, improve the completion record. If the quality standard is implicit, write it down with the person who reviews the work. If the outcome cannot be checked, decide whether that workflow is ready for more autonomy.

Finally, give the next assignment this closing requirement: return the result, the evidence that the acceptance criteria were met, and any unresolved exception. Keep that evidence short enough that someone will actually use it.

The aim is a handover that lets the recipient move forward with justified confidence. Once you have that, “done” becomes a useful operational fact instead of an attractive ending to a conversation.
